# План исправлений ReStore

## Объём и результат проверки

Витрина и админка используют Next.js 16.4.6 и React 19.3.1. FastAPI обрабатывает заказы, SQLite хранит платежи и очередь сообщений, HTTPX связывает приложение с Telegram и 2328.io. Проверены связи между обработчиками API, запросами хранилища, фоновыми задачами и интерфейсом оплаты. Локальный TypeScript прошёл проверку с параметрами --noEmit --incremental false. Платежи, отправка сообщений и развёртывание на Ubuntu не запускались. Ниже доказательства по исходникам, а проверки приёмки предназначены для изолированной среды.

Подтверждено 6 багов. Critical — 0, High — 2, Medium — 4, Low — 0. Изменение состава способов оплаты описано отдельно. Один сценарий восстановления криптосчёта оставлен на проверку.

## Состояние исправлений

Удалены выпуск и обработка Stars-счетов, режим PAYMENT_MODE и поля цен в Stars. Криптоплатежи 2328.io и бонусы используют RUB. СБП отображается как недоступная и отклоняется сервером до создания заказа.

При первом запуске сервер в одной транзакции удаляет заказы Stars/XTR, связанные уведомления, остатки XTR и старые колонки. В локальной базе до изменений заказов и бонусных остатков не было. На тестовой копии удаление старых записей сохранило криптозаказ, его уведомление и рублёвый баланс. Повторный запуск прошёл проверку.

Реализованы все шесть исправлений ниже. Проверка TypeScript и локальные сценарии FastAPI с подменой 2328.io и Telegram прошли. Осталась проверка восстановления в браузере и с реальным провайдером. Код и миграция на удалённое окружение не выкатывались.

Имя бота получается через getMe. Публичный адрес берётся из конфигурации деплоя или стандартной кнопки Mini App в меню Telegram. Уведомления идут по ADMIN_IDS, отдельные получатели остаются необязательной настройкой. Если ссылка на условия покупки отсутствует, витрина и API сообщают, почему оформление недоступно.

Перед боевым запуском учитывать правила Telegram для продаж цифровых товаров и услуг через ботов и Mini Apps. [Документация Telegram](https://core.telegram.org/bots/payments-stars)

## Подтверждённые баги в порядке приоритета

### 1. High — покупатель и менеджер теряют штатный путь к сверке проблемного криптоплатежа

backend/main.py:153–163, check_order; backend/store.py:137–142, orders; app/order.tsx:161–169. При review или expired интерфейс предлагает обратиться к менеджеру. Ручной запрос сверки для этих статусов возвращает старую запись, а админка показывает только paid и installed. Если позднее подтверждение не дошло через webhook, менеджер не видит заказ в рабочем списке и не может сверить его через админку.

1. Добавить менеджеру поиск проблемного заказа по номеру и явную сверку с payment/info. Переиспользовать выборку и фильтры из задачи 3.
2. Сохранять проверку суммы, валюты и идентификатора платежа. Проводить заказ только по подтверждённому paid или overpaid. Для AML и недоплаты сохранять статус проверки. [Статусы 2328.io](https://2328.io/api/payments#payment-edge-cases)
3. Проверить expired с последующим paid и пропущенным webhook. Менеджер должен найти и сверить заказ. Повтор сверки не должен дублировать начисление или уведомление. Проверить, что ответы aml_lock и underpaid оставляют заказ на проверке.

### 2. High — очередь уведомлений о платежах прекращает работу после ошибки SQLite

backend/integrations.py:214–226, deliver_messages; backend/main.py:22–32, lifespan. Ошибка SQLite в due_messages, finish_message или retry_message выходит за пределы цикла. Задача завершается, API продолжает обслуживать запросы, lifespan собирает результат задачи только при остановке. Даже после восстановления БД новые оплаченные заказы остаются без уведомления менеджеру.

1. Добавить обработку временной ошибки хранения с задержкой и журналированием, сохранив штатную отмену задачи.
2. Различать сбой чтения и сбой отметки уже отправленного сообщения. Учесть возможность повторной доставки во втором случае.
3. Однократно имитировать OperationalError при чтении очереди. После восстановления проверить доставку двух следующих сообщений без перезапуска API.

### 3. Medium — старый оплаченный заказ исчезает из рабочего списка менеджера

backend/store.py:137–142, Store.orders; app/admin/panel.tsx:112–120. Список объединяет paid и installed, сортирует по убыванию id и ограничивает результат 200 строками. Один неисполненный заказ и 200 более новых установленных заказов полностью скрывают первый заказ вместе с кнопкой завершения.

1. Добавить постраничную выборку с устойчивой сортировкой и фильтром по статусу.
2. Подключить навигацию в админке. Проверить описанный набор из 201 заказа и возможность отметить самый старый установленным.

### 4. Medium — ручная проверка платежа сообщает об отсутствии подтверждения при сбое провайдера

backend/integrations.py:142–148, refresh_crypto; backend/main.py:153–163, check_order; app/order.tsx, check. При тайм-ауте payment/info функция пишет предупреждение и возвращает локальную запись. API отвечает 200, а клиент для pending показывает, что подтверждение пока не поступило. Аналогично игнорируется False от update_crypto при несовпадении реквизитов.

1. Передавать результат неудачной сверки обработчику, возвращать различимую ошибку, сохранять последний известный статус.
2. Проверить тайм-аут, неверную сумму и успешный ответ pending. Только последний должен приводить к сообщению об отсутствии подтверждения.

### 5. Medium — неожиданный JSON от внешнего API обходит обработку ошибок

backend/integrations.py, Integrations.telegram и Integrations.crypto. При HTTP 200 с JSON null или массивом обе функции вызывают body.get и получают AttributeError. Telegram-ответ с ok=true без result вызывает KeyError. Эти исключения обходят преобразование в UpstreamError. В адаптере 2328.io исключение приводит к HTTP 500 при создании криптосчёта вместо предусмотренного ответа 502. В адаптере Telegram оно обходит штатную обработку ошибок отправки.

1. Проверять тип корневого объекта и наличие ожидаемых полей перед извлечением результата.
2. Подставить через HTTPX MockTransport три описанных ответа. Проверить тип исключения обоих адаптеров и ответ 502 при создании криптосчёта.

### 6. Medium — временный отказ Telegram теряет ответ на команду пользователя

backend/integrations.py:180–209, handle_update и poll. Если отправка приветствия на /start завершается UpstreamError, цикл журналирует ошибку и сохраняет offset следующего обновления. Команда считается обработанной, пользователь не получает кнопку открытия магазина.

1. Сохранять командный ответ в устойчивой очереди с уникальным ключом update_id до продвижения offset.
2. Имитировать временный отказ sendMessage, перезапуск и повтор входного обновления. После восстановления пользователь должен получить приветствие, очередь следующих обновлений должна продолжить обработку.

## Осталось проверить с провайдером

**Medium — восстановление криптосчёта после потерянного ответа.** Повтор оформления после закрытия диалога в том же сеансе витрины сохраняет requestId до успешного ответа. Повтор с тем же requestId проверен локально. Ключ сохраняется в sessionStorage и переживает перезагрузку в той же вкладке. Ранее созданный заказ также можно открыть из истории. В браузере и песочнице осталось проверить принятый запрос с потерянным ответом, повторное открытие диалога, восстановление из истории после полной перезагрузки и возможность намеренной повторной покупки. [Идемпотентность 2328.io](https://2328.io/api/payments#idempotency-and-retries)
